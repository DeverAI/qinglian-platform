# Design.md — 核心设计文档

> 本文档记录架构与设计决策，不涉及具体代码实现。

## 一、项目定位

面向青少年的互联网平台合规监督社区。青少年用户可举报互联网平台的不合理条款（隐私条款不合理 / 霸王条款 / 数据滥用 / 未成年人保护缺失等），经管理员审核后形成公开档案并在论坛展开讨论，配套积分激励、法律法规知识库与维权指引。

| 2026-08-08 | SID 会话密钥轮换安全升级 | 在鼠标握手基础上升级为 per-session SID 密钥体系：每次登录/注册/刷新签发唯一 `sid`（32 字节随机令牌），前端存储并通过 `X-SID` 头发送。后端以内存字典 `_sessions[sid] = {user_id, last_mouse_active, last_request_at, fail_count, created_at, rotated}` 跟踪每个会话。发言类端点校验 X-SID 有效且 sid 有近期鼠标活动；若请求缺少有效 sid 或 sid 无鼠标活动则记录 `fail_count`，连续失败达阈值（默认 3 次）判定为自动化访问（curl/爬虫或盗号），自动**轮换该用户全部 sid**：旧 sid 全部失效、写系统通知"检测到异常会话活动，会话密钥已自动轮换，可能是账号被盗或有人在进行爬虫操作，请检查账号安全并重新登录"、返回 code=4034。合法浏览器客户端（有鼠标活动）不受影响；若与爬虫共享同一 sid（令牌被盗），轮换后合法客户端也会收到 4034 并需重新登录，通知告知原因。 |
| 2026-08-08 | 安全系统自主升级 | 审查现有安全系统后发现隐患并自主升级：①原握手以 user_id 为键，同一用户多会话共享状态，无法区分爬虫与正常客户端 → 升级为 per-session sid；②原 CSRF Token 在 /me 响应中明文返回且存 localStorage，XSS 可窃取 → 维持现有设计（前端需 CSRF，无法避免），但增加 sid 作为第二道防线（XSS 窃取 localStorage 后仍需发送鼠标心跳才能通过握手）；③心跳端点无频率限制 → 增加 fail_count 机制防止心跳刷分；④root 账号握手豁免（root 双因素登录已保障安全）。 |
| 2026-08-08 | SID 握手安全漏洞修复与自主升级（第二轮） | 故障检测发现多项隐患并自主升级：①**心跳端点未检测 sid 轮换**——攻击者可对已吊销 sid 持续发送心跳维持会话 → 新增 `update_handshake_checked` 原子校验，sid 已轮换返回 4034；②**配置项 DoS**——`threshold_handshake_timeout`/`fail_limit` 不在 `DEFAULT_THRESHOLDS` 中且无最小值校验，root 误配 0 会导致全站非 root 用户无法发言或首次失败即轮换 → 纳入 `DEFAULT_THRESHOLDS`、新增 `THRESHOLD_MIN_VALUES` 硬下限、`_get_timeout`/`_get_fail_limit` 强制 `max()` 兜底；③**sid 归属校验缺失**——心跳/状态/登出端点不校验 sid 是否属于当前用户，攻击者可用自身令牌+受害者 sid 跨用户保活/清除会话 → 新增 `update_handshake_checked`/`get_handshake_status_for_user`/`clear_handshake_for_user` 三个归属感知函数；④**旧 sid 复用窗口**——login/refresh 签发新 sid 后旧 sid 仍有效约 180s → `_issue_session` 签发前调用 `invalidate_user_sids` 静默失效旧 sid；⑤**失败计数器内存放大**——高频失败请求可使 `_user_fails` 列表无限增长 → 单用户上限 200 条；⑥**前端后台标签心跳恢复迟缓**——浏览器后台节流导致 sid 超时 → 新增 `visibilitychange`/`focus` 监听切回前台立即补发心跳。 |
| 2026-08-08 | 鼠标握手机制定位澄清 | 握手机制定位为"会话活跃度检测"而非"绝对真人验证"——"鼠标活动"本质为客户端自证，脚本化客户端只需每 <60s 调用一次 `/auth/handshake` 即可绕过。该机制的实际价值在于：①提高自动化攻击成本（需模拟心跳）；②作为 CSRF+令牌窃取后的第二道防线；③fail_count 阈值轮换机制可识别"无鼠标活动的批量请求"模式。文档与代码注释中已明确此局限，避免过度信任。 |
| 2026-08-08 | 风控监控后台 | 服务器后台监控工具，专门用于风控审计与防护。核心设计：①**审计日志多处备份**——每次后台操作同时写入 DB `risk_audit_logs` + 文件 `storage/risk_audit/YYYYMM.log` + 高危操作额外写 `Err.log`，三处冗余防删除；②**风险分级**——基于方法/路径/action 评估为 info/warn/danger/critical 四级，批量删除/角色变更/封禁/服务开关/阈值修改为 critical；③**异常 IP 检测**——不在白名单 + 近 7 天未出现过 + 非本地 IP + 与用户历史常用 IP 不同 → 判定异常；④**双因素认证**——critical 级操作或异常 IP 自动触发 2FA，验证码 PBKDF2 哈希存储，配置邮箱则发邮件不返回明文（防中间人），3 次失败自动封禁 IP + 封禁用户（永久，需 root 手动解封）；⑤**令牌复用**——已验证 2FA 令牌绑定 actor_id，5 分钟内可复用，避免每个高危操作都重验；⑥**异常 IP 且未配置邮件时直接拦截**（code=4037），不把验证码暴露给可疑来源；⑦**封禁 IP 阻断后台访问**（code=4036），但不影响服务器 SSH（用户可通过云服务商安全组管理）。前端通过全局 `TwoFaManager` 自动拦截 4035 响应弹出验证码模态框，验证通过后自动重试原请求，对用户透明。 |

## 三、角色与权限模型

- **普通用户(user)**：注册登录、提交举报任务、论坛发帖/回复/点赞/收藏/举报、签到积分、收藏与积分记录查看。积分决定行为能力：0-3 分禁言；10 分可发起讨论版；30 分可接管并自管板块；200 分可创建群聊。
- **版主(moderator)**：普通用户权限 + 帖子加精、举报处理。
- **超级管理员(admin)**：版主权限 + 任务审核（通过/驳回/打回）、优秀案例评定、知识库管理、查看蜜罐日志、邮件服务器与 AI API 设置、权限申请审批。
- **系统管理员(sysadmin)**：超级管理员权限 + 用户角色管理、封禁账号与邮箱、查看管理日志。
- **Root(root)**：最高权限，独立于普通管理员；可开关普通服务、封禁管理员与设备、直接调整管理员角色；登录需双因素验证（密码+邮箱验证码）。
- 首个注册用户自动成为 sysadmin（系统初始化约定）；root 账号通过后端环境变量初始化，不可通过注册产生。

## 四、核心模块与开关

所有模块在配置中设有开关（ENABLE_XXX），关闭时不注册对应接口、前端隐藏所有入口，便于 demo 演示与排错：

1. **用户系统**：邮箱+密码注册，同一邮箱最多 2 个账号，同一邮箱多账号登录需提供昵称区分；声明"未满 18 岁需监护人知情"；注册时采集设备指纹（Canvas 指纹 + 屏幕分辨率等），同一指纹超过 3 个账号自动标记为"可疑"，由 sysadmin 人工审核是否刷分；注册前校验邮箱/设备是否已被封禁。JWT 访问令牌 7 天过期，刷新令牌 30 天自动续期；个人主页展示积分、历史任务、帖子、收藏。
2. **任务上传与审核（核心）**：表单含平台名称（下拉+自定义）、问题类型（五类）、条款原文（文本+截图最多 5 张）、不合理性说明、法律依据引用（可选）。状态机：待审核 → 审核中 → 已通过 / 已驳回（另支持"打回修改"）。通过后自动创建论坛板块，命名规则 `[平台名称] - [问题类型]`，审核全程留痕。**上传前用户自查**：用户必须勾选"已确认截图中不包含第三方个人信息"，否则无法提交。**AI 多模态合规检测**：提交后由管理员配置的多模态 AI 自动检测截图，若发现第三方个人信息等不合规内容，立即删除该图片并将任务置为"打回/待补充"。**审核截图时强制脱敏护栏**：管理员必须在界面确认无第三方个人信息，必要时使用 Canvas 打码；打码后的图片替换原图入库，原图不落地，打码行为写入 AdminLog。
3. **论坛系统**：板块按平台分类、按问题类型细分（树形结构）；帖子支持 Markdown、回复/引用、点赞/点踩、收藏、举报；标签系统（如 #霸王条款 #数据跨境）。
4. **积分系统**：每日签到 +1；上传证据 +2（管理员审核通过）；证据被标注有效 +3；撰写并代发邮件 +3；转发法律知识条文 +1；连续 7 天签到 +5；优秀举报案例额外 +5；帖子加精 +3；回复被点赞 ≥10 次 +1（仅触发一次）。**用途（非货币）**：50 分可改昵称颜色（荣誉），100 分可申请"内容审核志愿者"，500 分可申请管理员权限。**反刷规则**：禁止用户给自己的帖子/回复点赞或点踩；版主/管理员不能给自己的帖子加精。排行榜：周榜 / 月榜 / 总榜。
5. **知识库**：收录五部核心法律原文（《个人信息保护法》《未成年人保护法》《未成年人网络保护条例》《网络安全法》《数据安全法》），只引原文 + 官方来源链接，不做解读；提供"关键词→法律条款"索引表；每日推送一条法律原文（每日一法）。典型案例库、维权指南、Qoder 专项档案持续更新。
6. **邮件代发系统**：用户填写目标平台、问题类型、问题描述、涉及条款与证据后，系统自动生成标准化邮件；发送前必须全文预览并二次确认；平台统一邮箱（noreply@）代发，不暴露用户身份；发送即备份只读副本至后台；同时提供"自行发送"出口（复制模板+收件人地址）。后台通过 POP3 协议收取平台统一邮箱的收件箱，管理员可查看、标记已读，并可将邮件一键关联到论坛主题公开，便于跟踪平台回复与集体讨论。
7. **导航与快捷入口**：国家网信办举报中心 https://www.12377.cn/ 、工信部申诉平台 https://yhssglxt.miit.gov.cn/ 、法律全文链接。
8. **免责声明页**：不提供的法律咨询或代理；内容仅代表用户个人观点；平台尽审核义务但不对真实性担责；禁止商业行为与恶意攻击；平台保留政策修改权利。
9. **全局 AI 导游（已获用户许可）**：严格依据本 Design.md 原文解答项目疑惑；超出 Design.md 范围的需求统一记录到 Future.md，并返回标准话术"这个提议很好，已记录至 Future.md，将由管理员评估"，避免越界承诺。带独立开关，未配置 API 时降级为静态导览。AI API 参数支持后台即时配置。
10. **管理员设置**：后台可配置 POP3/SMTP 服务器（用于邮件代发与检测）、AI API URL/Key/Model，配置即时生效。
11. **Root 后台**：root 账号可查看服务开关、一键启停普通服务；查看管理员列表并直接授予/撤销 admin/sysadmin 角色或封禁管理员；查看与管理账号/邮箱/设备封禁记录。root 操作全程写入 AdminLog。
12. **私信与群聊**：
    - **私信**：用户一对一交流，支持未读计数，禁止发给自己。
    - **群聊（半私密空间）**：服务于投诉策略讨论、信息共享与互助、非正式社区社交；**不是证据归档区**，平台审查义务低于公开讨论版。
    - **准入门槛**：积分 ≥ 200 方可创建群聊或被任命为群管理员；200 积分 ≈ 67 封代发邮件 / 100 条有效证据 / 200 天签到，作为信用筛选。
    - **群主负责制**：群主可设公告、移除成员、解散群聊；平台不主动监控群内非红线内容。
    - **被动响应式治理**：平台仅在收到举报后介入；AI 30 秒内完成初步扫描：
      - 硬红线（涉政/涉黄/暴力/恐怖）确认违规 → 删除内容 + 封禁发布者 + 可能解散群聊；
      - 非红线但违反公序良俗 → 提醒群主处理，群主不作为则平台警告/移除成员；
      - 无明显违规 → 举报关闭；
      - 恶意举报 → 举报者扣 10-50 积分并警告，严重者封禁。
    - **复杂情况** 24 小时内转人工，逾期则再次调用 AI 全量上下文审核。
    - **积分奖惩**：
      - 建群一次性扣除 200 积分；积分低于 200 时群聊降级只读或解散；
      - 群稳定运行 30 天且无举报：群主 +10 积分；成员好评（可选）+1 积分/人/月，上限 +10；
      - 群内出现硬红线群主未处理：-50 积分；被举报 3 次以上查实：-30 积分；滥用管理权：-20 积分；群被强制解散：-100 积分 + 30 天禁建群。
    - **用户权益**：默认可搜索加入，群主可设审批；用户可自由退出；举报者身份对群主和成员匿名；消息保留 90 天（硬红线记录单独长期保留）；退出后历史消息仍保留，但用户可申请删除自己在群内的全部消息（提示他人可能已截图）；群解散时删除全部消息。
    - **免责声明**：群聊内容由用户自行发布，平台不对真实性、准确性、合法性作保证（依法必须介入的硬红线除外）；因信赖群聊内容导致的损失平台不承担责任；平台保留对违规群聊采取限制、解散、封禁等措施的权利。
13. **积分分层与社区行为门槛**：积分是行为信用的量化表现，直接决定用户可执行的操作：
    - 0-3 分：禁言（不能发帖/回复/私信/群聊发言），仅可签到（+1/天）和浏览；
    - ≥4 分：恢复发言；
    - ≥10 分：可发起新的讨论版（同一主题不可重复发起）；
    - ≥30 分：可接管并自管自己的讨论版；可认领已封存板块的代发邮件；
    - ≥200 分：可创建群聊或被任命为群管理员。
14. **讨论版生命周期与证据整理**：
    - 每个讨论版默认存在查重，提醒用户勿发重复内容；实锤重复（基础查重 1 天内能找到已存在内容）扣分并暂停 3 天 AI 审核内容的发言权。
    - 当版主/管理/AI/证据超过限额（默认 40 个）时，判定讨论区内容足够，自动**封存**：停止开放新内容，但用户仍可搜索；后续提交需经 AI 审核，确有必要的改进可加分，刷 token 则禁言 AI 审核内容并扣分，严重者封禁。
    - 封存 3 天后，平台正式召集用户写邮件；证据包经最终一轮 AI 审核整理，删除/增加/修改后合并为一份图片证据集 + 文字证据集 txt，定稿后任何人可认领下载。
    - 允许代发的板块：30+ 积分用户认领后须在 24 小时内产出至少可看的邮件初稿并经 AI 审核，否则释放额度并扣 2 积分；72 小时内需有活动迹象，用户可选择失联后将草稿与修改建议共享给下一人；同一人在同一板块最多认领 2 次，同时最多认领 2 个板块；只要通过初审（进入辩论阶段）即加激励积分，退出后若第一版过基础审核也加分。
    - 未允许代发的板块：封存后不召集写邮件，保留可搜索 3 周后归档；后续可针对相同厂商/产品发起新板块。
    - 部分板块默认不支持邮件代发，原因以板块置顶帖说明；可申请开放。
15. **邮件代发 AI 多模型辩论审核**：
    - 代发邮件先由 AI 初审，不合格直接退回；重复提交不改再发扣积分；明显刷 token 直接封禁。
    - 初审合格后进入 24 小时人工审核等待队列；人工未审核则触发多模型流程：
      - Deepseek / Qwen / MiniMax 负责"找茬式攻击"；
      - KIMI / Qwen 负责搜索验证问题是否存在；
      - 多模型评估风险后投票，最高五轮辩论；
      - 仅对争议较大或人工无法判断的申请启用完整五轮；明确严重的打回决定无需走完五轮。
    - 模型职责与列表由 root 在后台配置/修改/增加；管理员可申请 root 修改，修改前需测试 API 稳定性，出问题及时调整。
16. **反刷与内容治理**：
    - 频率限制：防止高频刷屏；
    - 字数门槛：字数太少不能过审；
    - 长文本自动转 txt 文件；
    - 图片自动压缩，单用户每日文字总量 ≤ 10k、图片总量 ≤ 4M；
    - 每天一次 AI 审核，触发危险关键词则立刻审核；
    - 任何审核流程中单独运行**攻击性内容检测程序**，识别要求 AI 忽略先前指示等攻击内容，存在则立即封禁该账户。
17. **Root 可配置阈值**：上述所有数字阈值（积分门槛、证据限额 40、封存天数 3、等待队列 24 小时、辩论轮数 5、内容上限 10k/4M 等）均由 root 在后台配置，管理员不可修改。

## 五、数据模型（九主模型 + 辅助表）

主模型：User、Task、Post、Reply、PointLog、KnowledgeEntry、Category、Tag、AdminLog、Email、Application、AdminSetting。
辅助表：点赞记录、收藏、举报、签到记录、帖子-标签关联、蜜罐日志、法律关键词索引（knowledge_keywords）、每日一法推送记录（daily_law）、POP3 收件箱（email_inbox）、Root 登录验证码（root_login_codes）、封禁记录（bans）、私信（messages/conversations）、群聊（groups/group_members/group_messages）、系统通知（system_messages）。
- Category 采用 parent_id 树形结构：一级为平台，二级为 `[平台] - [问题类型]` 板块。
- `users.email` 不再设唯一约束，通过应用层限制同一邮箱最多 2 个账号。
- `email_inbox` 新增 `post_id` 与 `is_public` 字段，用于关联论坛主题并公开邮件。
- `bans` 表记录账号/邮箱/设备三级封禁，登录与注册时联动校验。
- `root_login_codes` 表保存 Root 双因素登录的临时令牌与验证码，过期/使用后失效。
- 新增 `group_reports` 表记录群聊举报；`group_messages` 增加 `is_redline`/`is_deleted`/`ai_scan_at` 等字段支持红线检测与被动审核。
- 新增 `board_claims` 表记录用户认领封存板块代发邮件的进度、截止时间、共享草稿与状态。
- `categories` 增加 `status`（open/closed/archived）、`allow_email`、`evidence_count`、`closed_at`、`archived_at`、`claim_user_id` 等字段，支持讨论版生命周期。
- `posts`/`replies` 增加 `is_ai_reviewed`、`similar_to_id`、`word_count` 等字段，支持查重、字数门槛与 AI 审核。
- `admin_settings` 扩展为存储 root 可配置的阈值（积分门槛、证据限额、封存天数、等待小时、辩论轮数、每日内容上限等）。
- 新增 `system_messages` 表：存储首页系统通知（type/title/content/ref_type/ref_id/is_read/created_at），由审核流程、root 公告、讨论版生命周期等事件写入；首页 `/api/notify/messages` 拉取最近 20 条，支持单条删除、全部已读、清空。
- 新增 `board_subscriptions` 表：记录用户关注的论坛板块（user_id/category_id/created_at），首页消息流据此聚合关注板块新帖；同一板块重复关注走 upsert。
- 新增 `news` 表：存储 AI 夜间审核时联网搜索生成的新闻摘要（id/title/abstract/source_name/source_url/published_at/collected_at/is_active），首页新闻栏展示最近 7 天；超期自动置 is_active=0。
- 新增 `quiz_questions` 表：存储条文背诵选择题（id/knowledge_id/blank_text/options_json/answer_index/created_at），题目从知识库法律原文自动挖空生成。
- 新增 `quiz_records` 表：存储用户作答记录（id/user_id/question_id/is_correct/answered_at），用于防重复出题与每日上限校验（每日每用户最多 5 题计分）。

## 六、API 设计

- RESTful 风格，统一响应 `{ code: 0, message: "success", data: {...} }`，业务错误 code 非 0。
- 分页统一 `?page=1&limit=20`。
- 认证：Authorization: Bearer <access_token>；变更类请求额外要求 X-CSRF-Token 头。

## 七、安全设计

- **XSS**：服务端与前端双重转义；Markdown 渲染前先转义 HTML，再应用语法规则；链接仅允许 http/https。
- **CSRF**：登录下发 CSRF Token 并与账号绑定，所有变更类请求校验；认证使用 Bearer 头而非 Cookie，天然降低 CSRF 面。
- **文件上传**：仅 jpg/png/webp，校验扩展名 + 魔数；单张 ≤5MB，单次 ≤5 张；随机文件名落盘。审核通过前允许管理员使用 Canvas 打码脱敏，打码后的图片替换原图入库，原图不落地。
- **SQL 注入**：全程 sqlite3 参数化查询，禁止字符串拼接 SQL。
- **敏感操作留痕**：审核、加精、角色变更、封禁、截图打码等写入 AdminLog。
- **蜜罐**：前端源码故意保留"用户名 Cookie + 明文前端验证"诱饵（注释提示 role=admin 可进管理面板）；伪造 Cookie 访问诱饵面板/接口时，自动记录 IP、Cookie、路径至蜜罐日志，并展示在真实管理后台。
- **反刷与利益冲突**：禁止用户给自己的帖子/回复点赞或点踩；版主/管理员不得给自己的帖子加精；注册采集设备指纹，同一指纹超过 3 个账号自动标记为"可疑"。
- **Root 账号安全**：root 账号通过环境变量初始化，不在注册流程中产生；登录采用双因素认证（密码 + 6 位邮箱验证码），验证码仅发送至后端配置的固定邮箱，有效期 10 分钟，不暴露给前端。
- **多维度封禁**：`bans` 表支持账号、邮箱、设备三级封禁；登录、续期、注册时通过 `_check_bans` 联动校验；root 可封禁设备，管理员可封禁账号与邮箱；解封需同等或更高权限。
- **管理员权限自保护**：管理员不能封禁自己、不能修改自己的角色、不能给自己的帖子加精；最后一名 sysadmin 不可被降级或封禁；root 不可通过普通角色管理接口分配。
- **动态服务开关**：root 可通过 `/api/root/services/{name}` 启停普通服务；`service_switch_guard` 中间件实时拦截已关闭服务的 API 请求（认证、Root、配置接口除外），返回 503。
- **私信/群聊安全**：私信禁止发给自己，群聊仅成员可读写；内容 disclaimer 已写入免责声明页，平台仅提供传输与临时存储。
- **积分分层安全**：积分门槛在关键操作前校验（发帖/回复/发起讨论版/接管板块/建群），防止新注册用户或低信用用户刷屏、捣乱；0-3 分用户仅保留签到与浏览权限。
- **讨论版反刷**：基础查重（24 小时内相似内容）、频率限制、字数门槛、长文本转 txt、图片压缩；证据超过 root 配置限额后自动封存，停止新内容涌入；AI 每日巡查 + 危险关键词即时审核。
- **邮件代发安全**：AI 初审拦截不合格邮件，防刷 token；24 小时人工窗口 + 多模型辩论投票，兼顾效率与审慎；模型职责列表由 root 配置并支持 API 稳定性测试。
- **群聊红线拦截**：系统对硬红线（涉政/涉黄/暴力/恐怖）自动拦截并封禁；举报触发 AI 扫描，举报者身份对群成员匿名；恶意举报反噬举报者积分。
- **攻击性内容检测**：任何 AI 审核流程并行运行独立检测程序，识别"要求 AI 忽略先前指示"等 prompt 注入或越狱攻击，存在则立即封禁账号。
- **鼠标握手反爬（SID 会话密钥轮换体系）**：每次登录/注册/刷新签发唯一 `sid`（32 字节随机令牌），前端通过 `X-SID` 头发送。后端内存字典 `_sessions[sid]` 跟踪每个会话的 user_id、最后鼠标活跃时间、最后请求时间、失败计数、创建时间、是否已轮换。发言类端点校验 X-SID 有效且 sid 有近期鼠标活动（阈值默认 60 秒，root 可配置 `threshold_handshake_timeout`）；无有效 sid 或无鼠标活动时记录 `fail_count`，连续失败达阈值（默认 3 次，root 可配置 `threshold_handshake_fail_limit`）判定为自动化访问，**自动轮换该用户全部 sid**（旧 sid 失效）、写系统通知、返回 `code=4034`。临时性无活动返回 `code=4033`（请移动鼠标）。root 账号握手豁免（双因素登录已保障安全）。服务重启自动清零，不持久化。
- **错误兜底**：全局异常捕获，运行时错误一律写入项目根目录 Err.log，不得吞没。

## 八、页面结构

首页(Logo+每日简报+系统通知+消息流+新闻栏+游戏入口+导航+快捷入口) / 登录 / 注册 / 任务列表与提交 / 论坛板块 / 帖子详情 / 个人主页 / 知识库 / 排行榜 / 管理后台（含 Root 后台标签） / 免责声明 / AI 导游页 / 私信与群聊入口 / 条文背诵游戏页。

- 首页消息流：在简报与通知下方，按 Tab 筛选（全部/我的动态/关注板块/新闻）聚合展示；移动端单列堆叠，桌面端可双栏。
- 新闻栏：消息流的"新闻"Tab 主体，展示 AI 夜间生成的新闻摘要（abstract + 原文出处链接），保留 7 天。
- 条文背诵游戏页（/quiz.html）：展示当前题目（挖空条款 + 4 选项）、答题反馈、今日已答/已得分、积分规则说明；移动端适配大按钮触控。
- 全站移动端优化：导航可折叠、卡片单列、字号与触控区按 44px 最小命中、表格横向滚动、媒体查询断点 640px。
- 全站统一视觉规范：所有页面共享一致的导航栏（SVG Logo + 完整链接 + 汉堡菜单 + 主题切换按钮）、卡片圆角与阴影体系、按钮渐变与悬停动效、列表项组件化样式、空状态与骨架屏、toast 轻提示替代 alert/prompt、页面入场动画（IntersectionObserver 驱动）。鼠标握手遮罩在封禁期间覆盖全屏，阻止发言操作直到用户移动鼠标；检测到 sid 轮换（code=4034）时弹出醒目安全提醒模态框，告知用户"会话密钥已因异常活动自动轮换，可能是账号被盗或有人在进行爬虫操作"，需重新登录。
